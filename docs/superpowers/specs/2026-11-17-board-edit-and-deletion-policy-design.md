# Board 수정·삭제 정책 설계

## 의도

Board 게시물은 작성자가 내용을 수정하고 삭제할 수 있게 하되, 다른 회원의 권한·댓글·게시글 데이터가 잘못 변경되지 않도록 정책을 정한다. Product의 구매·버전 보존 정책을 그대로 적용하지 않고 게시판의 관계와 데이터 성격에 맞춰 결정한다.

## 범위

- 게시글 작성자가 제목, 본문, 태그를 수정한다.
- 게시글 작성자가 일반 삭제를 요청하면 게시글과 게시글 종속 데이터가 제거된다.
- API와 화면 모두 작성자만 수정·삭제 기능을 사용할 수 있게 한다.
- User 탈퇴, 운영자 강제 삭제, 신고·복구는 범위 밖이다.

## 도메인 판단과 정책 결정

- Board는 자유 토론형 게시물이다. Stack Overflow는 답변이 달린 지식 질문을 삭제하면 답변 맥락과 다른 사람의 기여가 손상될 수 있어 삭제를 제한하고 수정·운영자 검토를 대안으로 둔다. 이 서비스의 Board 댓글은 독립적인 답변/지식 기여로 관리되지 않으며 종속 FK와 cascade만 있다. 반대로 Reddit은 작성자 게시물 삭제를 지원한다. 따라서 작성자의 게시물 삭제를 허용하되 Board 댓글도 함께 제거하는 정책을 선택한다. 참고: [Stack Overflow 삭제 안내](https://stackoverflow.com/help/what-to-do-instead-of-deleting-question), [Reddit 개인정보 정책](https://redditinc.com/privacy).
- Product 삭제는 `saleStatus = WITHDRAWN`으로 판매만 중단하고 Product 행과 구매 버전은 보존한다. Board 삭제는 구매 권리가 없으므로 S3 정리 성공 후 Board와 종속 행을 물리 삭제한다. 비동기 정리 동안은 Board 행의 `deletionStatus`를 `DELETE_PENDING`으로 바꾸어 목록·상세·댓글에서 숨기고 이미지 키를 보존한다. S3 정리가 실패하면 `DELETE_FAILED`로 남겨 재전송할 수 있게 한다.
- 댓글(BoardChat)은 해당 게시글의 맥락에 속한다. 게시글 삭제 시 함께 삭제해 부모 글이 없는 대화를 남기지 않는다. BoardTag, BoardHit 및 BoardImage 행도 함께 삭제한다.
- 삭제 확인 UI는 게시글과 댓글이 함께 사라지며 되돌릴 수 없음을 알린다. 작성자 확인만으로 삭제를 수행하고 운영자 삭제/보존 요청은 별도 정책으로 둔다.
- 태그(BoardTag), 조회 기록(BoardHit), 이미지 참조(BoardImage)도 게시글 종속 데이터이므로 함께 삭제한다. 현재 Prisma 관계의 cascade 동작을 사용한다.
- 삭제된 게시글의 상세·댓글 URL은 더 이상 데이터를 반환하지 않는다. 검색·목록도 제거된 행을 조회하지 않는다.
- Board 전체 삭제는 Product 판매 중단 상태 패턴을 참고한다. API가 작성자 확인 후 `DELETE_PENDING` 상태를 먼저 기록하고 `{ operation: 'DELETE_BOARD', boardId }`를 SQS에 보낸다. SQS 전송 실패는 Board 행에 `DELETE_FAILED`와 오류를 보존한다. Lambda는 Board와 이미지 참조를 읽고 READY 이미지의 원본·파생 객체 및 PROCESSING/FAILED 이미지의 temp 객체를 삭제한 뒤 Board를 물리 삭제한다. 삭제 메시지가 DLQ에서도 처리되지 않으면 `DELETE_FAILED`로 남긴다. 배치 엔드포인트는 일정 시간 지난 PENDING/FAILED 행을 재전송한다. 배치는 Board 행을 삭제하지 않는다.
- BoardImage 일부 제거와 업로드 실패의 임시 파일 정리는 Board 행 상태만으로 표현하기 어려워 현재 StorageCleanupJob outbox를 유지한다. 이 outbox는 Board 전체 삭제 상태를 대신하지 않는다. CDN에는 고유 키를 사용하므로 객체 삭제 뒤 캐시 만료를 별도 요청하지 않는다.
- Board 이미지 편집은 업로드 화면과 동일하게 기존 갤러리를 유지한 채 새 이미지를 추가하고 썸네일 X로 개별 삭제한다. 유지되는 기존 이미지와 새 이미지의 합은 최대 3장이다. 새 이미지와 삭제 ID를 한 번에 저장할 수 있으며, 새 이미지 처리 큐 접수에 실패하면 기존 이미지 삭제는 반영하지 않는다.
- 수정은 작성자만 가능하다. 허용 필드는 제목, 본문, 태그, 이미지 갤러리(최대 3장)다. 카테고리와 댓글은 수정 요청에서 변경하지 않는다.
- 일반 삭제와 수정 모두 인증 사용자 ID를 서버에서 확인한다. UI 노출 제어는 편의를 위한 것이며 API 검증을 대체하지 않는다.
- Board 정책은 User 탈퇴 시 작성 게시물 처리 방식을 결정하지 않는다.

## 기존 구현 문제와 해결 상태

- 삭제 정책과 cascade 대상이 정해져 있지 않았다. → 작성자 직접 삭제, 댓글 동반 삭제, DB 종속 행 cascade 및 비가역 확인을 정책으로 명시했다.
- 수정 API가 작성자 소유권을 확인하지 않았다. → PUT에서 로그인 여부와 Board 작성자 ID를 확인하고, 미인증은 401, 비작성자는 403으로 거절한다. DELETE도 동일한 기준을 적용한다.
- 편집 화면이 제목·본문·태그만 수정하고 이미지 추가·개별 삭제를 지원하지 않았다. → 남은 자리만큼 파일을 추가하고 기존/새 이미지 모두 썸네일 X로 개별 제거한다. 새 파일은 presigned S3 업로드와 기존 BOARD SQS 계약으로 처리한다.
- SQS 접수 실패 때 수정 텍스트와 태그까지 일부 저장될 수 있었다. → 이미지 교체 시 큐 전송이 실패하면 새 이미지 행과 텍스트·태그 변경을 함께 되돌린다.
- 게시글 DB 행을 S3 정리보다 먼저 지우면 SQS 발행 실패 후 이미지 키를 잃는다. → Board를 `DELETE_PENDING`/`DELETE_FAILED`로 숨겨 보존하고 S3 정리 성공 후 물리 삭제한다. 일부 이미지 제거에는 StorageCleanupJob을 유지한다.
- 설정 화면이 소유자 여부와 관계없이 편집 폼을 노출하고 레거시 `UploadImage`를 사용했다. → 활성 설정 경로는 Product와 같은 `ProductEditor` 편집 모드로 전환했다. 로그인 사용자와 작성자가 일치할 때만 렌더링하고 API 검증도 별도로 유지한다. 레거시 설정 파일은 제거했다.

## 남은 운영 한계

- S3 삭제는 비동기이며 원본 SQS는 설정된 횟수만큼 재시도한 뒤 메시지를 DLQ로 보낸다. 원본 Lambda에는 `ReportBatchItemFailures`를 사용한다.
- DLQ Lambda의 트리거는 켜두되 `ReportBatchItemFailures`는 끈다. 처리 오류는 Lambda가 잡아 CloudWatch에 기록하고 Board를 `DELETE_FAILED`로 갱신한 뒤 정상 반환한다. 따라서 항목별 실패 응답은 재시도를 만들지 않고 메시지는 큐에서 제거된다. Lambda 자체의 시간 초과나 호출 실패는 다시 전달될 수 있다.
- `POST /api/cron/board-deletions`는 `DELETE_PENDING`/`DELETE_FAILED`를 SQS에 다시 보내는 수동 복구 경로다. 현재 자동 스케줄러는 연결하지 않는다. 실제 웹을 배포해 운영하다 자동 재전송이 필요해지면 스케줄러를 별도 연결하고, `DELETE_FAILED`를 자동으로 재시도할 정책도 함께 검토한다.
- 기존 Product 판매 중단은 이미지 또는 구매 버전을 삭제하지 않는다.

## 완료 기준

- 비작성자의 Board 수정·삭제 요청은 거절되고 DB 내용은 바뀌지 않는다.
- 작성자 수정은 제목, 본문, 태그를 저장하고 게시글 ID와 댓글을 유지한다. 기존 이미지는 개별 삭제가 선택된 경우에만 제거하고, 새 이미지는 기존 갤러리와 합쳐 최대 3장까지 추가한다.
- 작성자 삭제는 Board를 `DELETE_PENDING`으로 숨기고 S3 정리 성공 뒤 Board와 종속 DB 행을 물리 삭제한다. 전송·처리 실패 시 Board는 `DELETE_FAILED`로 남고 재전송할 수 있다.
- User 탈퇴, Product 정책, 테스트 코드는 변경하지 않는다.
- Product 일반 삭제/판매 중단 정책은 변경하지 않는다. Pro 구매 버전 파일을 보존한다.
